## 1. Summary

- **11 module schemas, 78 tables**, plus a `platform` schema of shared helper functions with no business data.
- Every entity in the Domain Model maps to a table here, and nothing new was added.
- **Tested on PostgreSQL 16:** the schema applies cleanly, and 15 tests using data from scenarios S06, S08 and S23/S26 all pass (section 6).

## 2. Design decisions in the schema (to confirm)

| # | Decision | Why |
|---|---|---|
| DM-9 | **No foreign keys between module schemas.** A reference to another module is a plain UUID, checked by the owning module's code. Foreign keys are used freely *inside* a module | Keeps modules separable (D-080/D-081). The cost: the database can't stop a cross-module reference pointing at nothing. Integration tests and the module interfaces cover that |
| DM-10 | **Fixed lists of values are stored as text with a check constraint**, not as Postgres enum types | Adding a value is a one-line migration; enum types are awkward to change |
| DM-11 | **Append-only is enforced by the database**: a trigger blocks UPDATE and DELETE on observations, events, evidence, relations, attestations, merges, resolution decisions, audit, reputation history, conflict activity and report snapshots | The guarantee doesn't depend on every developer remembering (D-020) |
| DM-12 | **Trust output is stored per derivation run.** Each recompute writes a new snapshot (assessments, facts, question statuses, record confidence) tagged with its run, rule-set version and as-of time. `trust.vehicle_current_run` points to the latest successful run | Any past answer can be explained and reproduced (G4, X2). Old runs can be pruned later without touching observations |
| DM-13 | **Conflicts live outside runs.** They have a human lifecycle: assignment, review, resolution | A reviewer's work must survive recomputation |
| DM-14 | **One outbox table per module** (`<schema>.outbox`) | Each module publishes its own events in the same transaction as its change (D-081 rule 2) |
| DM-15 | **Personal data sits in its own `pii` schema.** Names and phone numbers are stored as ciphertext produced by the app with cloud key management (KMS); phone numbers are matched by an HMAC hash | Can get its own database role, backup policy and erasure process (DM-2, P-013) |
| DM-16 | **IDs are generated by the app as UUIDv7** (`gen_random_uuid()` is only a fallback for manual inserts). Garage jobs created offline keep the ID the phone generated | Offline-safe and time-ordered (DM-8) |

## 3. What the database enforces vs. what the code enforces

| Rule | Enforced by |
|---|---|
| History can't be edited or deleted (D-020) | **Database** (DM-11 triggers) |
| A resent submission is stored once (X5) | **Database:** unique (source, idempotency_key) |
| An active VIN/chassis belongs to one vehicle (identity rule 1) | **Database:** partial unique index |
| A VIN is 17 characters with no I, O or Q | **Database:** check |
| Identifiers are stored normalized (uppercase, no spaces or dashes) | **Database:** check |
| Observation types must exist in the catalogue | **Database:** foreign key to `obs.observation_types` |
| A "merged" vehicle points to its survivor, and only then | **Database:** check |
| A health score can't exist without enough history (D-062) | **Database:** check |
| A resolved conflict records reasoning and a reviewer | **Database:** check |
| An attestation targets exactly one event or observation | **Database:** check |
| An approved organisation has an approval date | **Database:** check |
| A valuation's point lies inside its range | **Database:** check |
| Observation attributes match the type's schema | **Code:** Zod schemas shared by apps and backend; the JSON schema is stored in the catalogue |
| Required evidence present (D-057) | **Code** at Ingestion, using `observation_types.required_evidence` |
| Only approved organisations can submit (D-055, X4) | **Code** at Ingestion |
| Cross-module references point to real rows (DM-9) | **Code** + integration tests |
| Exposure filtering by audience | **Code** in Reports, using `report.exposure_policies` |
| All trust rules (C1–C10, question statuses, scores) | **Code** in Trust, Rule Set v1 |

## 4. Key tables explained

**`obs.observations`: the heart of SAZO.** One row per fact.
- `attributes` holds the type-specific data as JSON (DM-3). A GIN index makes searches like "which vehicle had engine 1NZ-B222222 fitted" fast.
- `event_time` + `event_time_precision` + `recorded_at` give the two times (D-021).
- `evidence_class` and `sensitivity` drive trust and exposure.
- There's no `updated_at` and no `deleted_at`, by design.

**`vehicle.vehicle_identifiers`.** VIN, chassis number, plates, engine numbers and import references, each with a validity period, status (`active` · `historical` · `disputed`) and, for plates, a `change_reason` (G6). A trigram index supports fuzzy "did you mean" search (G9).

**`ingest.submissions`.** Exactly what arrived, stored before anything is interpreted, with a SHA-256 hash of the payload. The idempotency key prevents duplicates.

**`trust.derivation_runs` + `trust.vehicle_current_run`.** Every screen reads "the current run" for a vehicle; every past run stays explainable.

**`report.exposure_policies`.** Observation type × attribute × audience → full / summarised / hidden. O-001 (finance and police detail) becomes rows in this table, not code changes.

**`garage.jobs`.** The only mutable working area in the garage flow: drafts created offline, holding the step-by-step answers. On submit, a job becomes an `ingest.submission` through the `garage_app` channel (DM-4). The job keeps a link to it.

## 5. Indexing and growth

- **Built for the expected reads:** a vehicle's observations by type and time; identifier lookup and fuzzy search; open conflicts for the review queue; unsent outbox events; queued SMS; anonymous search rate limits.
- **When `obs.observations` passes roughly 50–100 million rows,** partition it by hash of `vehicle_id`. Queries already filter by vehicle, so no query changes are needed. Trust run tables can be partitioned by time, with old runs pruned.
- **At the "Growth" stage (D-085),** move reads for public summaries and reports to a read-only replica of the database. The cache tables in `report` already separate those reads.

## 7. Operational notes for the build

- **Drizzle:** this SQL is the reference. Generate the Drizzle TypeScript schema from it (`drizzle-kit pull`), then use Drizzle migrations from then on. Triggers and functions stay as hand-written SQL migrations.
- **Database roles:**
  - The app uses one login role.
  - Writes to `pii` use a separate role that only the Observations module's code path can obtain.
  - Reporting/analytics users get read access to `report` and `trust` only.
- **Backups:** daily snapshots plus point-in-time recovery (RDS). `pii` erasure requests must also be honoured in backups by key rotation: deleting a party's encryption key makes old backup copies unreadable (crypto-shredding).
- **Simulated → real (X1):** handled by data in `ingest.sources`, with no schema change.
