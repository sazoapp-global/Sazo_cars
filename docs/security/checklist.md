# SAZO security checklist

Used by every security review (the `sazo-security-review` skill). Each line is a rule SAZO relies on and where it lives. Add a line whenever a review finds a new kind of problem, so the next review checks for it.

## 1. Access between people and businesses

- Every API route is either `@Public()`, has `@RequirePermission(...)`, checks the organisation with `canForOrg(...)` (+ organisation type), or only touches the caller's own rows (`actor.userId`). `scripts/security-scan.mjs` lists them; anything marked CHECK needs a reason.
- Organisation-scoped work (garage jobs, inspections, dealer stock, concerns, staff): the row's `organisation_id` must equal the `X-Organisation-Id` the caller is an *active* member of, and the organisation must be *approved* and of the right *type*. Look for `get(id)` / `job(id)` reads that don't compare `organisationId`. — `garage.service.ts`, `inspection.service.ts`, `dealer.service.ts`, `concern.service.ts`
- Person-scoped data (saved cars, share links, ownership claims, sessions, reviews): SQL filters on `user_id = actor.userId`. — `buyer.service.ts`, `ownership.service.ts`, `iam.repository.ts`, `community.service.ts`
- Evidence files: only the uploader and SAZO reviewers can open a file (`evidence.controller.ts` `file()`); photos referenced in a job/inspection/concern must have been uploaded by a member of that organisation (`evidenceErrors`).
- Garage visit answers by owners: only the confirmed owner, only visits in their ownership period, once (`ownership.service.ts`).
- Admin screens: the website hides them (`requireStaff`), but the API permission is the real check — every `/admin/*` route needs `@RequirePermission`.
- Partner submissions: a person may only send their source's record types (`DOMAIN_RECORD_TYPES`); capture channels (garage/inspector apps) build their own records.

## 2. Personal data (D-025, P-007, O-001, DPPA 2019)

- Names and phones exist only in `pii.parties` (AES-GCM + HMAC hash). Observations hold party ids; owner phones sent by registries are scrubbed *before* the raw payload is stored (`ObservationsService.withoutPersonalData`, `IngestionService.submit`).
- Buyer views (`reports.service.ts` `exposeObservation`): confidential records hidden (costs, sale prices, ownership parties), restricted records reduced to "exists" (police, finance, claims), `*PartyId` keys stripped. Snapshots/share links are built from the same view.
- Concern reporters are never named to buyers; reviewers' names never shown publicly; review authors: first name only.
- Garage customer phones are masked in the garage app; attestation links are single-use, stored as hashes, and not logged.
- Logs: no phone numbers, codes, tokens or names in application logs (the console SMS sender is for development only and must be off in production).
- Export (`/me/export`) only contains the caller's own data; deletion erases the pii record for their phone.

## 3. Sign-in and sessions

- Phone codes: HMAC-stored, 10-minute expiry, 5 attempts, 5 requests/hour/number, same response whether or not an account exists (`auth.service.ts`).
- Change-phone codes use their own purpose and are bound to the user; sign-in codes can't be used for it.
- Access tokens: HS256 pinned, issuer/audience checked, short-lived; the actor is reloaded from the database each request (suspension and deletion apply at once).
- Refresh tokens: random, only hashes stored, rotate on use; reuse after the grace window revokes the session.
- Sessions revoked on sign-out, phone change (other devices), account deletion.
- Website: tokens only in httpOnly, SameSite=Lax, Secure (in production) cookies; never sent to browser JavaScript. Phone app: refresh token in IndexedDB, access token in memory; cleared on sign-out.

## 4. Uploads and files

- Upload slot declares kind, size, sha256 and type; bytes are re-hashed on receipt and rejected on mismatch; write-once storage keys.
- Allowed types for people: JPEG, PNG, WebP, PDF (≤15 MB at the API, 8 MB on the website). JSON only for SAZO-written inspection reports.
- Files are served with `Content-Disposition: inline`, `nosniff`, and a sandbox CSP via `/admin/files/[id]` — never from a public URL.
- Storage keys are generated by SAZO, never from a filename (no path traversal).

## 5. Website and phone app

- Server actions call the API with the cookie token; the API does all permission checks. Never trust hidden form fields for authorisation.
- Redirect targets after sign-in go through `safeNext` (same-site paths only).
- No `dangerouslySetInnerHTML`. External links: `rel="noopener noreferrer"`, and `nofollow ugc` for user-submitted links.
- Security headers in `next.config.ts` (nosniff, frame DENY, referrer policy, permissions policy).
- Phone app service worker never caches `/v1/*` (personal data) — `navigateFallbackDenylist`.

## 6. Abuse limits

- Codes: 5/hour/number. Provisional cars: 5/day/person. Concerns: 10/day/business. Staff invitations: 3/minute/business. Business sign-ups: 3/day/person. Share links: 20/day/person. Dealer listings: 50/day/dealer. Reviews: one per person per model. Ownership: one live claim per person and car. Share links: random 128-bit tokens, 30-day expiry, revocable.
- Look for any new endpoint that creates rows or sends texts without a limit.
- A limit must check and write in one transaction behind a lock (`enforceLimit` in `platform/limits.ts`); a count followed by a separate insert can be beaten by sending requests at once.
- Buyers see record details only through `buyerVisibleAttributes` (declared fields only). New record types: check what that shows.

## 7. Secrets, config, dependencies

- `config.ts` refuses development secrets when `NODE_ENV=production`.
- No secrets in the repository (`git log -p | grep -i secret` for new ones).
- `npm audit --omit=dev` clean, or each finding explained.

## 8. Database

- The API connects as `sazo_app` (db/privileges.sql), never as the owner. `db/tests/app_role.sql` proves it cannot update/delete history, disable triggers, create/drop/truncate, or read the migration ledger. New tables are covered automatically (privileges are re-applied after every migration run).
- A business's own source (garage, inspector, real dealer) is written only by its workspace; the HTTP submission API refuses it (S1).
- Each business keeps its own copy of a person it told SAZO about (`recordPerson`); look for any new code that returns a stored name to someone who didn't type it (S2).
- Personal-data keys: KMS in production (config refuses otherwise); values carry their key version; rotation with `pii:new-key` + `pii:rotate`.
