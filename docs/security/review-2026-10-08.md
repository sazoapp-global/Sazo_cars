# SAZO security review — 8 October 2026

## Summary
Eight problems found: three High, three Medium, two Low. None was Critical — each needs a signed-in account, and most need a business SAZO has approved. The three High ones were fixed the same day, each with a test. The Medium and Low ones are waiting for decisions or are planned with launch preparation. Database hardening (limited login, key vault) was added at the same time.

## Findings

### S1 — A garage or inspector could send any kind of record onto any car (High) — **Fixed**
- **What could happen:** a manager of an approved garage or inspector could add records of any type — including a change of owner, a loan or a police record — to any car, bypassing the app's checks (photos, warnings).
- **Where:** `POST /v1/ingest/submissions` with the business's own source; proven by a test.
- **Fix:** sources belonging to a garage, inspector or (real) dealer only take records from their own workspace; the API refuses them here. Test: `garage.e2e.test.ts` "Security S1", `pipeline.e2e.test.ts`.

### S2 — A garage could learn a person's name from their phone number (High) — **Fixed**
- **What could happen:** if another garage had typed a customer's name and phone, a second garage typing the same phone saw that name.
- **Where:** garage job drafts (`garage.service.ts` saveDraft/view); proven by a test.
- **Fix:** each job keeps the customer exactly as that garage typed them (`PartiesService.recordPerson`); text opt-outs and erasure still apply to every record with the phone. Test: `garage.e2e.test.ts` "Security S2".

### S3 — A dealer could attach a made-up mileage to any car (High) — **Fixed**
- **What could happen:** a dealer could list any car with an invented high mileage and no photo, making a later true reading look like a rollback.
- **Where:** `POST /v1/dealer/stock`; proven by a test.
- **Fix:** a mileage needs an odometer photo taken by someone at that dealer; at most 50 new listings a day per dealer. Test: `dealer.e2e.test.ts`.

### S4 — The 10-a-day limit on reported problems can be beaten by sending many at once (Medium) — open
- **Where:** `concern.service.ts` (count, then insert); proven by a test.
- **Fix:** make the count and insert one atomic step (a lock per business, or a database counter).

### S5 — Several actions have no limit (Medium) — open, **decision needed**
- **What could happen:** one person or business could send many texts (codes to many numbers, staff invitations) costing SMS money, or create many uploads, share links, business sign-ups or logbook claims.
- **Fix:** per-person and per-IP limits on texts and creation, and a general request limit at the edge (web firewall) once hosted.
- **Decision needed:** the limits (suggested: 3 staff invitations a minute per business; 20 share links a day per person; 3 business sign-ups a day per person).

### S6 — Some customs/insurance fields reach buyers unchanged (Medium) — open
- **What could happen:** a free-text field a partner fills in (e.g. a name inside an insurance record) is shown to buyers as entered.
- **Where:** `reports.service.ts` `exposeObservation`; proven by a test.
- **Fix:** show buyers only the fields listed for each record type (an allow-list), not everything the record holds.

### L1 — Files fetched straight from the API lack protective headers (Low) — open
- **Fix:** add `X-Content-Type-Options: nosniff` and a sandbox CSP on `GET /v1/evidence/:id/content` too (the website's file route already has them).

### L2 — Without `NODE_ENV=production`, the API starts with development secrets (Low) — open
- **Fix:** refuse to start with development secrets whenever it is not on a developer's machine (e.g. when `PUBLIC_WEB_URL` is not localhost), and set `NODE_ENV=production` in the hosting setup.

## To watch
- Garage free-text fields that buyers can see (notes, repair descriptions) — moderate or limit later.
- Auction prices are shown to buyers — confirm this is wanted (business decision).
- `safeNext` (sign-in redirect) — add a test for control characters.
- Verification-document file ids are not checked against who uploaded them.
- Unexpected errors are logged in full — check no personal data reaches logs once hosted.
- Vehicle references use `Math.random` — not secret, but switch to crypto for tidiness.

## Checked and fine
- **Access between businesses:** garage, inspection, dealer and concern routes check the organisation, its approval and its type.
- **Own data:** saved cars, share links, sessions and claims only touch the caller's rows.
- **Admin:** every admin route has a permission.
- **Sign-in:** codes, refresh rotation and revocation behave as designed; website cookies are httpOnly.
- **Website:** security headers are set.
- **Phone app:** does not cache API answers, and is wiped on sign-out.

## Database hardening added with this review
- **Limited login:** the API now has its own login, `sazo_app` (`db/privileges.sql`). It can read and write rows but cannot change history tables, switch off their protection, change the structure or read the migration list. Proven by `db/tests/app_role.sql`; every browser test now runs the API with this login.
- **Personal-data keys:**
  - In production the keys come from AWS KMS (`PII_KEY_SOURCE=kms`), and the API refuses to start otherwise.
  - Every value records its key version, so keys can be replaced: `npm run pii:new-key` makes a new key and `npm run pii:rotate` moves old records onto it. Proven by `keyring.test.ts` and `pii-keys.e2e.test.ts`.
